# Measured: Keepass2Android's background synchronization with nobody to answer

Run 2026-11-16 on the Android emulator of `measured-k2a-synchronize.md`, to close the questions that
report left open: what "Synchronize in background" does when the program is not in front to ask,
what "Cancel" at the question during a synchronize leaves, and whether the settings considered for a
phone (the program's own access to the server, "Always merge on conflict" on, background
synchronization as the File handling screen leaves it) lose anything over a longer sequence.

**Everything in the tables is measured**: the server's file and Keepass2Android's cached copy at
named points of each run, read with KeePassLib 2.62. What is read from its source (`v1.15-r6`,
commit `bbcf3787c75b`) is in prose and marked **read**.

## 1. How the runs were made

Only what differs from `measured-k2a-synchronize.md` 1 is written here; the program, the emulator
`kpg30`, the WebDAV server (rclone v1.68.2 under WSL, its own invented password for these runs),
the opening flow, the preference states A and B, the two copies SOLD and SNEW-fixed with their
items and the read-back `sverdict.sh` are that report's.

- **The program**: the installed package hashed again before the first run,
  `5c446a4fff3ac3fe29b07724dff59e756738eb1fd6611281cd594e421817891d`, the pinned value; version
  1.15-r6 (code 254). The emulator was started without wiping, booted in 54 s.
- **Holding the background synchronization at its first request.** With "Synchronize in
  background" on, a save writes the cache only and starts a synchronization at once (read, below).
  To put the program in the state a case names before that synchronization reaches the server, the
  run stops the server's process (`server.sh freeze`, SIGSTOP) before the save: the kernel still
  accepts the connection and the request waits unanswered; after the state is set the process is
  continued (`thaw`, SIGCONT) and the request is answered. The program's read timeout for WebDAV is
  60 s (read: `WebDavStorage.java:233-235`); no hold lasted that long.
- **Watching** (`watch.sh`): every 2 s, the server's file hash, the cache's `.version` and
  `.baseversion`, and the title and text of every notification of the program, each change logged
  with its time. `notif.sh` logs the notifications in full from `dumpsys notification --noredact`
  (channel, flags, title, text, actions). `devstate.sh` logs the screen's state, the program's
  process and its foreground service. `snap.sh` keeps the server's file and the cache at a named
  point; `kill9.sh` kills the process with SIGKILL as root.
- **The desktop's turns** in section 4 are `deskstep.sh`: the probe's new `deskstep` command
  (`probe\Store.cs`) applied to the server's file as it is at that moment, written beside it and
  renamed over it.
- **The device log.** After the crash of section 2 the later runs went through `run-sy2.sh`,
  `run-sy.sh` with the device log cleared at the start and its fatal exceptions kept at the end
  (`logs\sync\<run>.logcat.txt`); the crash's own excerpt was taken from the device's log buffer
  after that run.
- **SFTP** (section 5): the same rclone serving the same directory with `rclone serve sftp` on port
  2022, password authentication, an invented password of its own, host keys generated by rclone
  into the measurement's directory and deleted at the end (`server-sftp.sh`); opened through the
  program's "SFTP (SSH File Transfer)" storage (`flows\k2a-sftp-open.flow`).

**Counted**: runs whose flow ended without a failure, **16 runs**: 11 in section 2 (the first
run, `bg-b-amcoff-r1`, and the three repeats after the crash among them), 2 in section 3, 1 in
section 4 and 2 in section 5; 11 + 2 + 1 + 2 = 16. **Not counted**, kept in `runs\sync-not-counted\` and `logs\sync-not-counted\`: the first run of
each SFTP case (2 runs), whose flow did not answer the program's second host key question
("…/files/known_hosts does not exist. Are you sure you want to create it?") and stopped at the file
list; both left the server's file as put there.

**The evidence** is in `android-evidence\k2a-background\` beside this report: `base\` the dumps of
SOLD and SNEW-fixed; `runs\<run>\` the dumps of the server's file and the cache at each named point
(`server-<point>`, `cache-<point>`, the run's end as `server` and `cache`), the desktop's turns
(`desk-*`), the phone's copy before the last synchronize and the run's SNEW where a run has them,
and KeePass's own Synchronize (`keepass-sync\`), each with its diffs against SOLD and SNEW;
`logs\sync\<run>.log` every step, dialog, notification, watch line, preference and file hash;
`logs\sverdicts.txt` the read-back line of every file; `logs\expect-*.txt` the comparisons with
KeePass's Synchronize; `logs\emu-*.log` the emulator's log; `server\` the servers' logs, the fetch
script and the published `SHA256SUMS`; `flows\`, `scripts\`, `probe\`. Machine paths are written
`<work>`, the WSL user `<user>` and its home `<wsl-home>`. No database is copied.

## 6. Read from the source

**Read**, `src/Kp2aBusinessLogic/database/edit/SaveDB.cs:127-135`: with "Synchronize in background"
on, a save switches the cached storage to offline, writes the cache only and marks that a
synchronization must follow; `:230-243` starts it (`SynchronizeCachedDatabase`) through the
operation runner when the save finishes. The conflict check of the save itself is skipped in that
mode (`:152`, `!requiresSubsequentSync`). `SynchronizeCachedDatabase.cs:84-110`: when the server's
file differs from the cache's base version and the cache holds local changes, it runs a save with
the server's data as the original file, which asks "Merge changes?" unless "Always merge on
conflict" is stored true (`SaveDB.cs:157-197`).

**Read**, where the question goes: `app/App.cs:777-806` posts it to the main thread and
`:668-774` shows it only if the program's active context is an activity; otherwise it leaves the
question pending and sets the operation's sub-message to "User interaction required. Please open
the app." (`Resources/values/strings.xml:1336`). An activity that resumes sets the active context
and shows the pending question (`app/App.cs:1570-1578`, `LifecycleAwareActivity.cs:92,109`). When the
program goes to the background with an operation running, the operation runner starts
`BackgroundSyncService` (`OperationRunner.cs:231-242`), a foreground service whose ongoing, silent,
low-priority notification carries the operation's message as its title and the sub-message as its
text, with no action but opening the program (`services/BackgroundSyncService.cs:81-110`); the
service makes itself the active context (`:68`), which is not an activity, so the question is not
shown while the program is away. The dialog is built non-cancelable (`app/App.cs:736-739`).

**Read**, what starts a synchronization by itself: a save (above); opening the database from the
cache when the cache may differ from the server (`PasswordActivity.cs:1654-1673`, `LoadDB.cs:112-119`);
and, only while a group list is on screen, a check every 20 s (`GroupBaseActivity.cs:345-366`) that
starts one when one is pending for want of the allowed Wi-Fi or when the periodic background
synchronization is on and its interval has passed (`SyncUtil.cs:148-169`); the periodic one is off
by default (`Resources/xml/pref_app_file_handling.xml:41-45`). Nothing else: no timer, no network
listener, no job outside the program's own screens.

## 7. Not run, and why

- **More repeats.** Each state with the merge setting off ran once, and states a and c with it on
  once; state d with it on ran three times because of the crash, and state b twice. The usage
  budget of this measurement went to the other items.
- **A second save while the question stands**: not possible on this release. The dialog is not
  cancelable (BACK left it in all four "off" runs), it comes back whenever any of the program's
  screens resumes, and after a restart the open synchronizes and raises it again before the group
  list can be reached (4 runs of 4). So the case "the question never answered, then a second save"
  has no second save; what was measured is the question left standing through HOME, a
  force-stop and a restart, with nothing written to the server or the cache.
- **The periodic background synchronization** and "Synchronize only on Wi-Fi": off by default
  (read, section 6), not turned on.
- **A long time with the screen off** (Doze, app standby, battery optimization): the screen was
  off for about 60 s per run, the emulator on external power; not run.
- **A kill by the system under memory pressure**, and a kill in the middle of an upload: SIGKILL
  after the save was used instead; not run.
- **A crash's reproduction on demand**: the race of section 2 was seen once in 7 runs that merged
  without a question; no run was made to provoke it.
- **The six-turn sequence more than once**, and with the merge setting off: one run, as advised.
- **HTTPS, Nextcloud or ownCloud, Google Drive, Dropbox, OneDrive, FTP, Samba**: not run; SFTP is
  section 5.
- **KeePass on the desktop** reading the merged files: read with KeePassLib 2.62 headless, and
  KeePass's own Synchronize run headless on the same copies (section 4); KeePass's window not
  started.
- **Any device but this emulator**, any Android but 11.

## 8. What a phone with "Always merge on conflict" loses

Measured on Keepass2Android 1.15-r6, the file opened through the program's own WebDAV access (and,
for section 5's two cases, its SFTP access), "Always merge on conflict" turned on on the File
handling screen, which in every such run also showed and stored "Synchronize in background" on.

**No sequence measured here lost another writer's change.** With the setting on, no "Merge
changes?" question appeared in any of the 8 runs that had it (7 in section 2, 1 in section 4), and
every synchronization that met a changed server's file merged: with the program in front on
another screen, in the background, with the screen off, at the first unlock after the process had
been killed, at a second save, and over the six alternating turns with the server away twice. The
server's file afterwards held every item the desktop had written (the write-once `KPG.` entry, the
database custom data key, both deletion records and the deletion they record, every password)
and every change of the phone; where both sides changed a password, the newer was current and the
other in the entry's history, and at the equal second both were kept (the phone's current, the
desktop's in history). Compared with KeePass's own Synchronize of the same two copies, nothing
KeePass keeps was missing.

**Every sequence found that loses another writer's change** is one that needs the question, which
the setting takes away (read: `SaveDB.cs:161-167` merges without asking whenever the setting is
stored true, on a save and on a synchronize alike): the server's file changed since the phone
last loaded it, the phone has an unsent change, and **"No, overwrite"** is answered
(`measured-overwrite.md` 5, `measured-k2a-synchronize.md` 7; 3 runs of 3 and 18 of 18 there). On a
phone where the setting is off, that answer stays reachable at every save and synchronize,
including on return after a background synchronization (section 2: the question waited, with
nothing written, through HOME, a screen off, a force-stop and a restart, for whoever next opened
the program). **Cancel** loses nothing (section 3).

**What the setting does not cover**, each measured or read here, none of them a loss of another
writer's change:

- **The setting belongs to the installation, not to the database.** It is a stored preference of
  the program; cleared data, a reinstall or another phone start without it (read: its default is
  false, `Resources/xml/pref_app_file_handling.xml:136-142`), and then the question, with its "No,
  overwrite", is back.
- **A phone's own change made while the server is unreachable waits in its cache**, with no
  question, message or notification (section 4, turns 4 and 6), and **no synchronization starts by
  itself when the server is back** (section 4: 60 s watched; read, section 6: only a save, an open,
  the periodic synchronization when turned on, or the menu start one). Until the next save, open or
  "Synchronize database...", the desktop does not see that change, and a phone lost or cleared in
  between loses it: its own change, not another writer's.
- **A crash after a background merge** (section 2, 1 run of 7 with the setting on): the merged file
  had reached the server and the cache before it, and nothing was lost; the program was simply not
  running afterwards, with nothing shown. Read: the race behind it can only begin after the merged
  file is written (`SaveDB.cs:279-283`, the save before the post), so it cannot cost the merge.

**Whether the advice can be given as worded.** For the measured server types, "open the database
through the program's own access to the server, turn 'Always merge on conflict' on, never answer
'No, overwrite'" held in every run here, and with the setting on the third clause has nothing left
to act on. It needs one condition added, and one recommended: the setting must be checked on
**every** phone and again after any reinstall or cleared data (the screen shows it; the question
appearing at all means it is off), and after working away from the server, "Synchronize
database..." once the server is reachable, so that the phone's own changes reach the desktop. Not
measured, and so not covered: servers other than WebDAV and SFTP, long screen-off periods under
Doze, and a kill during an upload (section 7).
